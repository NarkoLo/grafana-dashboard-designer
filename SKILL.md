# Grafana Dashboard Designer

Создавать дашборд как интерфейс принятия решений, а не как коллекцию доступных метрик. Сохранять связь между вопросом пользователя, сигналом, запросом и визуализацией.

## Порядок работы

1. Определить аудиторию, объект наблюдения и решения, которые должны приниматься по дашборду.
2. Инвентаризировать источники данных, метрики, лейблы, логи, трейсы, существующие дашборды и ограничения Grafana.
3. Составить краткий контракт дашборда: цель, охват, переменные, ключевые вопросы, допустимая задержка и частота обновления.
4. Спроектировать информационную иерархию по `references/ux-rules.md`.
5. Подобрать запросы по `references/query-rules.md`. Не выдумывать метрики и лейблы: сначала проверять их через MCP, API или предоставленные пользователем данные.
6. Создать или изменить dashboard JSON. За основу разрешается брать `assets/service-overview.dashboard.json`.
7. Проверить JSON командой:

   ```bash
   python3 scripts/validate_dashboard.py dashboard.json --strict
   ```

8. Если доступен Grafana MCP, действовать по `references/grafana-mcp.md`: сначала читать, затем планировать изменения, после записи перечитывать результат.
9. Отдать пользователю JSON или применить изменения только в пределах явно разрешённого экземпляра Grafana. Кратко перечислить принятые UX-решения, допущения и оставшиеся пробелы в данных.

## Обязательные правила

- Размещать на первом экране здоровье сервиса и сигналы, требующие действия.
- Строить путь `обнаружение → локализация → диагностика`; подробные таблицы и логи располагать ниже.
- Различать ошибку запроса, `No data`, ноль и отсутствие серии.
- Применять согласованные единицы, разрядность, цвета и диапазоны времени.
- Не использовать красный как декоративный цвет. Резервировать его для опасного состояния.
- Ограничивать сравнительные графики читаемым числом серий; высокую кардинальность переносить в drill-down.
- Делать заголовок панели ответом на вопрос или названием измеряемого состояния, а описание — подсказкой по интерпретации.
- Не кодировать окружение, namespace, pod или instance прямо в запросах, если они должны быть переменными.
- Не скрывать качество данных: явно показывать задержку, пропуски и источник.
- Не публиковать изменения в Grafana без проверки запросов и JSON.

## Выбор результата

- Для обсуждения архитектуры выдавать спецификацию рядов и панелей до JSON.
- Для GitOps выдавать детерминированный dashboard JSON без серверных `id` и `version`, если репозиторий не требует иного.
- Для существующего дашборда сохранять UID, ссылки, переменные и намеренные пользовательские настройки.
- Для прямой интеграции использовать Grafana MCP, если он доступен; иначе использовать HTTP API или подготовить JSON для импорта.
- При недостатке данных выдавать макет с отмеченными неизвестными, а не придумывать работающие запросы.

## Проверка готовности skill

После изменения самого skill выполнять:

```bash
python3 scripts/healthcheck.py
```

Healthcheck должен завершиться кодом `0`. Предупреждения валидатора дашборда в режиме `--strict` считаются ошибками качества.
