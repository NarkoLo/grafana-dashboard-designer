# UX-правила Grafana-дашбордов

## Контракт дашборда

До создания панелей зафиксировать:

- аудиторию: дежурный инженер, разработчик, владелец продукта или руководство;
- объект: сервис, пользовательский сценарий, инфраструктурный узел или SLO;
- решение: что пользователь должен понять или сделать за 30 секунд;
- охват: окружения, кластеры, регионы, namespace и сервисы;
- рабочий диапазон времени и допустимую задержку данных;
- ссылки на runbook, логи, трейсы и дочерние дашборды.

Если эти сведения неизвестны, задать короткие вопросы. При невозможности получить ответ явно отметить допущения.

## Иерархия

### Первый экран: обнаружение

Разместить 4–8 наиболее важных показателей:

- доступность или SLO;
- скорость запросов/операций;
- доля ошибок;
- latency в одном или нескольких целевых перцентилях;
- насыщение критического ресурса;
- свежесть данных или время последнего успешного события.

Использовать Stat только для значения, которое можно интерпретировать без дополнительного графика. Добавлять sparkline, когда направление изменения важно.

### Второй уровень: локализация

Разделить проблему по полезным измерениям: endpoint, status class, dependency, instance, consumer group, database или node. Не показывать одновременно десятки series. Оставить Top N и дать drill-down.

### Третий уровень: диагностика

Показывать ресурсы и внутренние механизмы: CPU, память, GC, connection pools, очереди, retries, Kafka lag, БД, логи и трейсы. Эти панели не должны вытеснять пользовательское здоровье сервиса с первого экрана.

## Компоновка

- Использовать сетку шириной 24 колонки.
- Делать Stat-панели одинаковой высоты и ширины в одном ряду.
- Группировать панели строками по вопросу, а не по источнику данных.
- Не смешивать масштабы с несовместимыми единицами на одной оси без явной причины.
- Избегать горизонтальной прокрутки и наложения панелей.
- Сворачивать редко используемые диагностические ряды, если это сокращает шум.

## Заголовки и описания

Хорошие заголовки:

- `Доля HTTP 5xx`
- `p95 времени ответа`
- `Отставание consumer group`
- `Инстансы без успешного scrape`

Плохие заголовки: `HTTP`, `Errors`, `Graph 1`, имя метрики без контекста.

В description указывать смысл, единицу, способ агрегации, допустимый диапазон и действие при проблеме. Не повторять заголовок.

## Цвет, пороги и доступность

- Резервировать красный для аварийного состояния, жёлтый — для риска, зелёный — для нормы.
- Не полагаться только на цвет: использовать подписи, значения и пороги.
- Не использовать более 6–8 цветов одновременно без необходимости.
- Для нескольких панелей одного типа применять одинаковые пороги.
- Не задавать порог без связи с SLO, лимитом ресурса или подтверждённой эксплуатационной нормой.

## Единицы и точность

- Выбирать встроенную единицу Grafana: `percentunit`, `reqps`, `s`, `ms`, `bytes`, `Bps`, `short` и другие подходящие единицы.
- Для долей 0–1 использовать `percentunit`; для значений 0–100 — `percent`.
- Не показывать лишние десятичные знаки.
- Не смешивать rate и абсолютное количество без явного обозначения.

## Переменные

Расположить слева направо:

`environment → cluster → namespace → service → instance → dependency`

- Использовать chaining, если множество значений велико.
- Не включать `All`, если запрос с ним создаёт опасную кардинальность или бессмысленную агрегацию.
- Экранировать regex-переменные и использовать корректные операторы `=~`/`!~`.
- Не скрывать переменную, существенно меняющую смысл дашборда.

## Состояния данных

- Ноль означает измеренное нулевое значение.
- `No data` означает отсутствие подходящих series.
- Ошибка datasource означает, что состояние системы неизвестно.
- Устаревшие данные нужно обозначать отдельным сигналом свежести.

Не преобразовывать отсутствие данных в ноль, если это маскирует отказ telemetry pipeline.

## Антипаттерны

- Один дашборд для руководителя, дежурного и разработчика одновременно.
- Десятки Stat-панелей без тренда и контекста.
- Красно-зелёная радуга для обычных series.
- Автоматически сгенерированные заголовки из имён метрик.
- Сырые pod/instance-графики на первом экране.
- Переменная `interval`, позволяющая пользователю случайно создать дорогой запрос.
- Таблица логов вместо сигнала ошибки.
- Копирование одинакового запроса в десятки панелей без recording rule или переменной.

## Финальное ревью

Проверить:

1. Понятно ли состояние системы за 30 секунд?
2. Видно ли, какой сигнал требует действия?
3. Можно ли локализовать проблему за 2–3 перехода?
4. Различаются ли ошибка данных, отсутствие данных и ноль?
5. Согласованы ли единицы, цвета и пороги?
6. Не перегружены ли запросы высокой кардинальностью?
7. Работают ли переменные при одиночном и множественном выборе?
8. Есть ли путь к логам, трейсам или runbook?
